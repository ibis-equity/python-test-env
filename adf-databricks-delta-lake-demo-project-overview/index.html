ADF + Databricks + Delta Lake Demo

Retail Order Lakehouse Architecture for Batch, Streaming, Quality, and BI

Project overview

This project tells a complete data engineering story: raw order data lands in a lakehouse, gets validated, transformed through medallion layers, and is turned into trusted business metrics for reporting.

The repository connects Azure Data Factory, ADLS Gen2, Databricks, Delta Lake, Delta Live Tables, and Power BI into a realistic end-to-end platform pattern. The emphasis is not just on moving files; it is about ensuring quality, governance, and operational visibility as data moves from source to insight.

Business use case

  • Capture orders from both batch uploads and live event streams.
  • Normalize raw payloads into a reliable and consistent schema.
  • Reject malformed records before they contaminate analytic tables.
  • Build silver and gold datasets for operational and executive reporting.
  • Support monitoring, troubleshooting, and service health checks.
The key idea behind this repo is simple: a modern data platform is not only about pipelines. It is about data trust, data quality, and the operational discipline required to make analytics usable for real business decisions.

Core architecture

1. Ingestion

  • ADF orchestrates the scheduled and triggered flow.
  • Batch and stream order data lands in ADLS under landing folders.
  • Databricks notebooks read the raw files into a bronze layer.
  • Streaming ingestion uses Auto Loader and checkpointed incremental reads.

2. Transformation

  • Bronze stores raw transactional records with minimal transformations.
  • Silver cleans, deduplicates, validates, and enriches the data.
  • Gold exposes curated business-ready metrics and marts.
  • PySpark and Spark SQL coordinate the ELT pattern.

3. Consumption

  • Power BI consumes the trusted datasets and presents business dashboards.
  • Monitoring queries help track freshness, quality, and operational health.
  • DLT expectations expose failed records and quality drift.
  • Ops assets help with triage and demo walkthroughs.

Lakehouse layer model
  • Bronze: raw data preserved in a near-original state.
  • Silver: cleaned and quality-checked business data.
  • Gold: aggregated, business-facing metrics and marts.
  • Quarantine: invalid rows are isolated for troubleshooting and reprocessing.
Why the validation layer matters
  • Bad rows cannot be silently accepted into the curated layer.
  • Rules check required fields, timezone-aware timestamps, positive quantities, and valid prices.
  • DLT expectations and Python validation act as the first line of quality defense.
  • Operational teams can identify poor source data quickly instead of discovering issues in reports.

The validation layer in src/quality/rules.py

validate_order_record()

This function validates a single order dictionary and returns a structured result indicating whether the record passed or failed. It enforces checks for required fields, timestamp validity, quantity constraints, and currency precision.

  • Rejects missing or blank values.
  • Requires valid ISO timestamps with timezone metadata.
  • Requires positive whole-number quantities.
  • Rejects non-positive or over-precise prices.

split_valid_invalid()

This helper partitions a batch of records into pass/fail buckets. It is useful when the ingestion pipeline wants to keep clean records flowing while routing bad data to quarantine or review paths.

  • Returns valid records and invalid records separately.
  • Makes quality enforcement easy to reason about in batch flows.
  • Supports clean handoff to downstream lakehouse logic.

Behavior example

The validation logic is intentionally explicit. A record is not just marked invalid generically; it receives a clear reason such as invalid_quantity, invalid_order_ts, or invalid_unit_price.

  • Good data passes with reason = "ok".
  • Bad data is contextualized for support and debugging.
  • Tests in tests/test_rules.py protect the current behavior.
In other words, the validation layer is the discipline behind the architecture: it stops noisy data from polluting the silver and gold layers.

Deployment scripts in scripts/

Bash deployment: scripts/deploy_adf_cli.sh

export RESOURCE_GROUP="rg-adf-demo" export LOCATION="eastus" export FACTORY_NAME="adf-demo-lakehouse" export GIT_URL="https://github.com/<your-user>/<repo>.git" export GIT_BRANCH="main" ./scripts/deploy_adf_cli.sh

This script logs into Azure, creates the resource group, creates the Azure Data Factory, and provisions the linked services, datasets, pipelines, and trigger definitions packaged in the repo. It is ideal for Bash-based environments and lab setups.

PowerShell deployment: scripts/deploy_adf_cli.ps1

$env:RESOURCE_GROUP = "rg-adf-demo" $env:LOCATION = "eastus" $env:FACTORY_NAME = "adf-demo-lakehouse" $env:GIT_URL = "https://github.com/<your-user>/<repo>.git" $env:GIT_BRANCH = "main" .\scripts\deploy_adf_cli.ps1

This is the Windows-friendly equivalent. It performs the same core deployment work and avoids recreating the process manually in the Azure portal. It is especially helpful for engineers working in PowerShell-based DevOps or local admin workflows.

What the deployment scripts automate
  • Validate Azure CLI login state.
  • Create or reuse the target resource group.
  • Create the Azure Data Factory if it does not exist.
  • Create linked services for ADLS and Databricks.
  • Create required datasets, pipelines, and trigger artifacts.
  • Optionally connect the factory to Git when a repository URL is provided.
Why this matters
  • Deployments become repeatable and easier to explain in a demo.
  • Less manual setup means more attention can be paid to architecture.
  • These scripts sit right at the intersection of cloud infrastructure and data platform delivery.
  • They represent the practical first step from repo to running Azure resources.
