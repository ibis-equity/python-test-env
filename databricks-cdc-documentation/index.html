How to Add Secrets

  1. Go to your GitHub repository
  2. Click Settings
  3. Select Secrets and variables > Actions
  4. Click New repository secret
  5. Add the secret name and value
  6. Click Add secret

Getting Databricks Credentials

Host (Workspace URL)

  1. Go to your Databricks workspace
  2. Copy the URL from your browser: https://adb-xxxxxxxxxxxx.azuredatabricks.net
  3. This is your DATABRICKS_*_HOST

Token (Personal Access Token)

  1. Go to Databricks workspace
  2. Click your profile icon → User settings
  3. Click Developer tab
  4. Click Generate new token
  5. Copy the token value (it won't be shown again)
  6. This is your DATABRICKS_*_TOKEN

Security Best Practices

  • ✅ Use separate tokens for each environment (dev, qa, prod)
  • ✅ Rotate tokens regularly (every 90 days recommended)
  • ✅ Don't commit secrets to the repository
  • ✅ Use repository environment protection rules for prod
  • ✅ Review GitHub Actions logs carefully (secrets are masked)

Testing Secret Configuration

To verify secrets are available to workflows:

gh secret list --repo your-org/db-cdc

Revoking Secrets

If a secret is compromised:

  1. Generate a new token in Databricks
  2. Update the corresponding GitHub secret
  3. Rotate all credentials if needed

ARCHITECTURE.md

Architecture Decisions

Data Pipeline Architecture

Bronze Layer (Raw)

  • Source: Kafka topics
  • Storage: Delta Lake (append-only)
  • Purpose: Immutable record of all CDC events
  • Retention: 30 days (configurable)

Silver Layer (Processed)

  • Source: Bronze layer via streaming
  • Storage: Delta Lake (deduplicated, partitioned)
  • Purpose: Cleaned, deduplicated CDC records
  • Transformations:
  • Remove duplicate events
  • Add change hash for tracking
  • Mark deleted records
  • Attach metadata (processed_at, etc.)

Gold Layer (Analytics)

  • Source: Silver layer (batch)
  • Storage: Delta Lake (optimized)
  • Purpose: Aggregations and statistics
  • Examples:
  • Table summaries
  • Change statistics by operation type
  • Daily/hourly metrics

Technology Choices

Why Databricks + Delta Lake?

  1. ACID Transactions - Ensure data consistency
  2. Time Travel - Roll back to previous states
  3. Schema Evolution - Handle schema changes gracefully
  4. Unified Analytics - SQL + Python + ML in one platform
  5. Data Lineage - Track data flow with Unity Catalog

Why Kafka?

  1. Decoupling - Decouples source systems from Databricks
  2. Buffering - Handles spikes in data volume
  3. Replay Capability - Can replay events from any point
  4. Scalability - Linear scalability to millions of events/sec
  5. Ecosystem - Works with Confluent, Aiven, Azure Event Hubs

Why Structured Streaming?

  1. Exactly-once Semantics - No duplicates with checkpointing
  2. Late Data Handling - Processes late-arriving events
  3. Stateful Processing - Handles complex CDC logic
  4. Integration - Native Databricks integration

CDC Strategy

Change Capture Patterns

INSERT → Add new record to Silver
UPDATE → Update existing record with new values
DELETE → Mark record as deleted (soft delete)

Deduplication Strategy

Window-based Deduplication:

ROW_NUMBER() OVER (PARTITION BY record_id ORDER BY timestamp DESC)

Rationale: Keeps latest version of each record, handles out-of-order events.

Deployment Strategy

Dev Environment

  • Local Kafka via docker-compose
  • 2-worker Databricks cluster
  • 30-second processing intervals (faster feedback)
  • Debug-level logging

Prod Environment

  • Azure Event Hubs (managed Kafka)
  • 4-16 worker auto-scaling cluster
  • 1-5 second processing intervals (low latency)
  • Info-level logging, comprehensive monitoring

Scalability Considerations

Horizontal Scaling

  • Kafka partitions → Databricks task parallelism
  • Worker count → Process more data in parallel
  • Batch size → Balance latency vs throughput

Data Volume Estimates

  • Small: <1 million events/day → 2-4 workers
  • Medium: 1-100 million events/day → 4-8 workers
  • Large: >100 million events/day → 8+ workers with auto-scaling

Error Handling

Retry Logic

max_retries = 3
backoff_ms = 1000

Dead Letter Queue Strategy

  • Failed records written to separate table
  • Manual review and reprocessing queue
  • Alerts triggered for DLQ entries

Data Quality Framework

Multi-layer Validation

  1. Schema Validation - Matches expected structure
  2. Null Checks - Critical columns non-null
  3. Deduplication - No exact duplicates
  4. Freshness - Data within acceptable age
  5. Business Rules - Custom validations

Security Considerations

Credential Management

  • Databricks Secrets for Kafka credentials
  • No credentials in source code
  • Separate dev/prod credentials

Data Encryption

  • TLS for Kafka communication
  • Encryption at rest in Delta Lake
  • Column-level encryption for PII (optional)

Monitoring Strategy

Key Metrics

  • Throughput: Records per second
  • Latency: End-to-end delay
  • Data Quality: Error rates, null percentages
  • System Health: Job failures, cluster health

Alerting Thresholds

  • High latency: Consumer lag > 100K
  • Error rate > 5%
  • Data age > 24 hours
  • Job failures trigger immediate alert

Cost Optimization

Strategies

  1. Auto-termination: Clusters shut down after 30 minutes idle
  2. Spot instances: Use cheaper spot instances where possible
  3. Partitioning: Prune unnecessary data in queries
  4. Compression: Use snappy compression for storage
  5. Archival: Move old data to cheaper storage (S3/ADLS)

CDC_HOW_IT_WORKS.md

How CDC (Change Data Capture) Works - Complete Explanation

1. What is CDC?

Change Data Capture (CDC) is a technology that identifies, captures, and delivers changes made to data in a database in real-time or near real-time.

Simple Explanation

Imagine you have a database of customers. Someone updates a customer's email address. CDC captures this change and records: - WHAT changed (email field) - WHEN it changed (timestamp) - WHERE it changed (customers table, record ID 123) - WHY it changed (old value vs new value) - HOW it changed (UPDATE operation)

Visual Example

Database                        CDC System
┌─────────────────┐            ┌──────────────┐
│ customers table │            │ Change Log   │
├─────────────────┤            ├──────────────┤
│ id: 123         │  UPDATE    │ op: UPDATE   │
│ email: old@...  │   ───────→ │ id: 123      │
│                 │   capture  │ field: email │
└─────────────────┘            │ old: old@... │
                                │ new: new@... │
                                │ time: 14:22  │
                                └──────────────┘

2. Why Do We Need CDC?

Problem It Solves

Traditional Data Integration (Batch)

Source Database          Full Extract (every night)
└─ 1,000,000 records     └─ Scan all records
   Updated 100 today        Copy all 1,000,000
                            Find 100 changes (wasted time)
                            Latency: ~12 hours later

With CDC (Streaming)

Source Database          CDC Capture (continuous)
└─ 100 changes today    └─ Capture only 100
   At any time              Changes available immediately
                            Latency: seconds

Real-World Use Cases

Use Case Problem Solution
Real-time Analytics Dashboard stale (updated nightly) CDC: Update dashboard as data changes
Data Sync Two systems out of sync CDC: Keep systems synchronized live
Audit Trail Cannot track who changed what CDC: Record all changes with metadata
Machine Learning Model trained on old data CDC: Retrain model with latest changes
Search Indexing Search index outdated CDC: Update search indexes in real-time
Data Warehouse EDW updated once daily CDC: Update EDW continuously

3. How CDC Captures Changes

Method 1: Query-Based CDC

Approach: Poll database periodically and compare

Time 1:                    Time 2:
┌──────────────┐          ┌──────────────┐
│ ID=1 v=100   │   Sync   │ ID=1 v=102   │
│ ID=2 v=200   │ ──────→  │ ID=2 v=200   │  Changes:
│              │  Query   │ ID=3 v=300   │  • ID=1: 100→102
└──────────────┘          └──────────────┘  • ID=3: NEW

Pros: Simple, works with any database
Cons: Resource intensive, batch-like, high latency

Method 2: Log-Based CDC

Approach: Read from database transaction log

Database Transaction Log
├─ INSERT customers(ID=1, name=John)
├─ INSERT customers(ID=2, name=Jane)
├─ UPDATE customers SET email='john@ex.com' WHERE ID=1
├─ DELETE customers WHERE ID=2
└─ INSERT customers(ID=3, name=Bob)

CDC extracts these events:
└─ Customer 1: INSERT
└─ Customer 2: INSERT
└─ Customer 1: UPDATE (email)
└─ Customer 2: DELETE
└─ Customer 3: INSERT

Pros: Real-time, low overhead, captures all operations Cons: Database-specific, more complex

Method 3: Trigger-Based CDC

Approach: Database triggers fire on changes

Source Table (customers)
├─ INSERT TRIGGER
├─ UPDATE TRIGGER
└─ DELETE TRIGGER

Triggered events write to:
└─ CDC Change Table

Example trigger:
CREATE TRIGGER after_customer_update
AFTER UPDATE ON customers
FOR EACH ROW
INSERT INTO cdc_log VALUES (
  'UPDATE', 
  NEW.id, 
  OLD.email, 
  NEW.email
)

Pros: Captures exact operations, low latency Cons: Requires database modifications, potential performance impact

4. CDC Delivery Patterns

Pattern 1: Insert-Only

Events are appended to a changelog (never updated):

CDC Log (append-only)
├─ op=INSERT, id=1, time=14:00
├─ op=UPDATE, id=1, time=14:05
├─ op=UPDATE, id=1, time=14:10
├─ op=DELETE, id=1, time=14:15
└─ op=INSERT, id=1, time=14:20

Downstream sees:
1. Record 1 inserted
2. Record 1 updated
3. Record 1 updated again
4. Record 1 deleted
5. Record 1 re-inserted

Use case: Audit trails, history tracking

Pattern 2: Upsert-Only

Keep only latest version per record:

CDC Table (upsert)
├─ id=1, data={...}, version=5
├─ id=2, data={...}, version=3
└─ id=3, data={...}, version=1

New update comes in:
id=1 updated → Replace row with new data

Result:
├─ id=1, data={...}, version=6  (updated)
├─ id=2, data={...}, version=3  (unchanged)
└─ id=3, data={...}, version=1  (unchanged)

Use case: Current state, real-time analytics

5. CDC Delivery Guarantees

At-Most-Once

"Each change delivered zero or one time"

Problem: Changes can be lost
├─ Database commit: ✓
├─ Send to CDC: ✓
├─ Network fails: ✗
└─ CDC never received it

Result: Change lost forever

Used for: Non-critical notifications

At-Least-Once

"Each change delivered one or more times"

Success:
├─ Database commit: ✓
├─ Send to CDC: ✓
├─ Acknowledge: ✓

Failure & Retry:
├─ Database commit: ✓
├─ Send to CDC: ✓
├─ Network fails: ✗
├─ Retry and send again: ✓
└─ Acknowledge: ✓

Result: Change delivered (possibly twice)

Used for: Most systems (Kafka default)

Exactly-Once

"Each change delivered exactly one time"

With Idempotent Processing:
├─ Change ID = abc123 arrives
├─ Process and apply
├─ Store "abc123 processed"
├─ Duplicate arrives
├─ Detect "abc123 already processed"
├─ Skip it

Result: Change processed exactly once

Used for: Critical financial/billing systems

8. CDC Challenges & Solutions

Challenge 1: Duplicate Events

Problem:

Network Issue:
Send event to Kafka → Network fails → Retry
Kafka receives it twice
Downstream sees duplicate

Solution: Deduplication

Track processed event IDs:
Event ID: abc-123 arrives
├─ Check: Is abc-123 already processed?
├─ No → Process it, store abc-123
└─ Yes → Skip it

Duplicate arrives:
├─ Check: Is abc-123 already processed?
├─ Yes → Skip it (already processed)

Challenge 2: Out-of-Order Events

Problem:

Network delay:
Event 1: UPDATE email to new@ex.com (timestamp 14:00)
Event 2: UPDATE email to final@ex.com (timestamp 14:05)

Arrives out of order:
Event 2 arrives first (14:05)
Event 1 arrives late (14:00)

If applied in arrival order:
1. Apply Event 2: email = final@ex.com ✓
2. Apply Event 1: email = new@ex.com ✗ (wrong!)

Result: Data is wrong!

Solution: Timestamp Ordering

Store events with timestamps:
Event 1: ts=14:00, email=new@ex.com
Event 2: ts=14:05, email=final@ex.com

Before applying:
Sort by timestamp ascending:
Event 1 (14:00) → Apply first
Event 2 (14:05) → Apply second

Result: Correct final state (email = final@ex.com)

Challenge 3: High Latency

Problem:

Query-based CDC:
Night batch: Query all 1,000,000 records
Find 100 changes
Write to warehouse
Result: Data available 12 hours later

Solution: Streaming CDC

Log-based CDC:
Real-time capture: 100 changes detected
Immediately published: Available now
Stream to warehouse: Updated instantly
Result: Data available seconds later

Challenge 4: Large Tables

Problem:

Query-based on 1 billion row table:
Query all rows: Takes 30 minutes
Network transfer: Another 10 minutes
Database load: Very high
Result: Slow, resource intensive

Solution: Log-based + Filtering

Log-based CDC:
Capture changes: Automatic, minimal overhead
Publish to topic: Only the 100 changes, not 1B rows
Network transfer: 100 events, not 1B rows
Database load: Minimal

cdc_processor.py - Comprehensive Documentation

Module Overview

The cdc_processor.py module is the heart of the CDC (Change Data Capture) processing pipeline. It processes raw CDC events from the Bronze layer and transforms them into deduplicated, production-ready data in the Silver layer.

What Does It Do?

High-Level Purpose

Transforms raw Kafka CDC events into clean, deduplicated records:

Bronze Layer (Raw)          CDC Processor          Silver Layer (Processed)
├─ Duplicates               ├─ Read                ├─ Single version per record
├─ Out-of-order             ├─ Transform           ├─ Deletion tracked
├─ Mixed operations         ├─ Deduplicate        ├─ Change hash calculated
└─ Multiple versions        └─ Write               └─ Ready for analytics

Module Structure

Class: CDCProcessor

Main class that orchestrates the entire streaming pipeline.

Methods:

  1. __init__(config) - Initializes the processor with configuration - Creates SparkSession for distributed computing - Extracts Delta Lake and streaming configs - Called once at job startup

  2. read_bronze(table_name) - Reads raw CDC events from Bronze layer (streaming) - Returns a PySpark streaming DataFrame - Connects to Delta table with readStream API - Input: Raw events from Kafka - Output: Streaming DataFrame

  3. apply_cdc_logic(df) - Transforms raw events with 3 key operations:

    • Calculate change hash: MD5(id + data) - detects what changed
    • Add timestamp: When change was processed
    • Flag deletions: is_deleted boolean for soft deletes
    • Normalizes column names
    • Input: Raw streaming DataFrame
    • Output: Transformed DataFrame with CDC metadata

  4. dedup_changes(df) - Removes duplicate records - Keeps only the most recent version per record - Uses window function with row_number - Handles out-of-order events correctly - Input: Transformed DataFrame - Output: Deduplicated DataFrame

  5. write_to_silver(df, target_table) - Writes processed data to Silver layer (streaming) - Uses Delta Lake checkpointing for fault tolerance - Enables schema evolution - Runs indefinitely (blocks until error/stop) - Input: Deduplicated DataFrame - Output: Data written to Silver table

  6. run() - Main orchestration method - Chains all transformations together - Handles errors with logging and re-raising - Flow: read → transform → deduplicate → write

Data Flow Explained

Step-by-Step Process

1. READ BRONZE
   ↓
   Raw CDC events with:
   - id: Record ID
   - source_table: Origin table name
   - operation: INSERT, UPDATE, or DELETE
   - timestamp: Event time
   - data: Current record state (JSON)
   - before: Previous state for UPDATEs
   - ingested_at: When entered Bronze

2. APPLY CDC LOGIC
   ↓
   Calculate and add:
   - change_hash = MD5(id | data)
     Purpose: Identify what changed
     Use: Skip processing if hash unchanged

   - processed_at = current_timestamp()
     Purpose: Audit trail
     Use: Track processing latency

   - is_deleted = (operation == "DELETE") ? true : false
     Purpose: Soft delete for history
     Use: Can restore deleted data

3. DEDUPLICATE CHANGES
   ↓
   Window function groups by (record_id, source_table)
   Orders by timestamp descending
   Keeps only first row (most recent)

   Result: One version per record

   Example:
   Event 1: user_123, UPDATE, ts=100, data={email: "new@ex.com"}
   Event 2: user_123, UPDATE, ts=50, data={email: "old@ex.com"} (late)
   Event 3: user_123, UPDATE, ts=100, data={email: "new@ex.com"} (dup)

   → Keeps only Event 1 (ts=100, most recent)

4. WRITE TO SILVER
   ↓
   Streaming write with:
   - Checkpoint for fault tolerance
   - Schema evolution allowed
   - Append mode (add to existing)
   - Processing trigger (5 second batches)

   Result: Delta table with processed records

Why Deduplication?

Multiple copies of same event can occur:

Reasons for Duplicates:
├─ Retry logic: Failed Kafka produce → retry
├─ Rebalancing: Partition rebalance → reprocess
├─ At-least-once: Kafka delivery guarantee
└─ Processing failures: Job restart from checkpoint

Deduplication keeps only latest version per record
Uses most recent timestamp as source of truth

Why Change Hash?

MD5 hash of (id + data) helps:

change_hash = MD5("user_123" | "{name: John, email: john@ex.com}")

Benefits:
├─ Quick comparison: Compare hashes instead of full data
├─ Detect changes: If hash same as before, data unchanged
├─ Reduce noise: Don't process unchanged data
└─ Track history: Can see what changed without comparing values

Why Soft Deletes?

is_deleted flag instead of removing records:

Hard Delete (removes data):        Soft Delete (marks as deleted):
┌──────────────┐                   ┌──────────────────┐
│ user_123     │  DELETE           │ user_123         │
│ (removed)    │  →  Gone!         │ is_deleted=true  │
└──────────────┘                   │ (preserved)      │
                                    └──────────────────┘

Soft delete advantages:
├─ Audit trail: See what was deleted and when
├─ Recovery: Can restore deleted data
├─ Analytics: Know deleted records exist
└─ Compliance: Retain data history for audits

Error Handling

The run() method wraps everything in try-except:

try:
    # Pipeline execution
    logger.info("Starting...")
    bronze_df = read_bronze()
    cdc_df = apply_cdc_logic(bronze_df)

    raise  # Re-raise for visibility

Streaming vs Batch Processing

This processor uses Streaming:

Streaming Approach (Used Here):
├─ Continuous processing
├─ Low latency (seconds)
├─ Processes events as they arrive
├─ Infinite until stopped
├─ Checkpointing for fault tolerance
└─ Use: Real-time analytics, up-to-date data

Batch Approach (Alternative):
├─ Process scheduled intervals
├─ Higher latency (minutes/hours)
├─ Waits for batch window
├─ Finite processing
├─ Simpler recovery
└─ Use: Daily reports, historical processing

Exactly-Once Semantics

How does it prevent duplicates?

Kafka Guarantee: At-least-once delivery
CDC Processor Response:

1. Kafka sends event                Event: ID=123, v=1
2. Processor writes to Bronze       Bronze: ID=123, v=1, offset=100
3. Processor writes checkpoint       Checkpoint: offset=100
4. If crash before step 3: Reprocess from offset=99 (duplicate)
5. If crash after step 3: Resume from offset=101 (skip duplicate)

Deduplication catches remaining duplicates:
- Window function keeps only latest
- Timestamp used to determine "latest"
- Any duplicate with older timestamp discarded

Common Issues & Solutions

Issue: Duplicates in Silver Layer

Cause: Deduplication not working Solution: - Check timestamp column exists - Verify window partition columns correct - Ensure Spark version ≥ 3.0 (row_number support)

Issue: Slow Processing

Cause: Too many duplicates or large batches Solution: - Increase worker count - Reduce processing_time trigger - Enable caching for large datasets

Issue: Checkpoint Errors

Cause: Checkpoint location invalid Solution: - Verify checkpoint_location path exists - Check write permissions - Clear checkpoint and restart if corrupted

Issue: Out-of-Memory

Cause: Window function on too much data Solution: - Partition by source_table before processing - Reduce batch size with maxOffsetsPerTrigger - Increase executor memory

CDC Challenges & Solutions

Challenge 1: Duplicate Events

Problem:
Network sends → Kafka acknowledgement timeout
Network resends same event → Kafka receives duplicate

Time    Event
─────   ──────────────────────
14:00   Send Event A to Kafka
14:01   No acknowledgement (network slow)
14:02   Resend Event A
14:03   Kafka receives Event A (first time)
14:04   Kafka receives Event A (duplicate!)

Result: Downstream processes Event A twice!

Solution: Deduplication
────────────────────

Track processed events:
processedEvents = {Event_A_123, Event_B_456, ...}

When Event A arrives:
1. Check: Is Event_A_123 already processed?
   No → Process it, add to set

Duplicate arrives:
1. Check: Is Event_A_123 already processed?
   Yes → Skip it (already processed!)

Result: Event processed exactly once ✓

Challenge 2: Out-of-Order Events

Problem:
Event 1: 14:00 - Update email to new@ex.com
Event 2: 14:05 - Update email to final@ex.com

Arrives out of order:
14:03 - Event 2 arrives (early by 2 seconds)
14:06 - Event 1 arrives (late by 6 seconds)

If processed in arrival order:
1. Process Event 2: email = final@ex.com ✓
2. Process Event 1: email = new@ex.com ✗ WRONG!

Final state: email = new@ex.com (incorrect!)

Solution: Timestamp Ordering
───────────────────────────

Store events with timestamps:
Event_1: ts=14:00, email=new@ex.com
Event_2: ts=14:05, email=final@ex.com

Before processing:
Sort by timestamp (oldest first):
1. Event_1 (ts=14:00) → Process first
2. Event_2 (ts=14:05) → Process second

Result: Final state = final@ex.com (correct!) ✓

Challenge 3: Data Consistency

Problem:
Multiple events for same record:

Event 1: Customer 1 name=John (ts=14:00)
Event 2: Customer 1 name=John (ts=14:00) [duplicate]
Event 3: Customer 1 email=new@ex.com (ts=14:01)
Event 4: Customer 1 email=final@ex.com (ts=14:02)

Which state is correct?
Customer 1 {name=John, email=final@ex.com} ✓

Solution: Deduplication + Timestamp
──────────────────────────────────

1. Deduplicate: Keep 1 copy per timestamp
   Ts=14:00: ONE Event (John)
   Ts=14:01: ONE Event (new@ex.com)
   Ts=14:02: ONE Event (final@ex.com)

2. Order by timestamp
   Earliest first: John → new@ → final@

Result: Correct current state ✓

Problem: Workflow exceeded 360 minutes

Solution: 1. Check for long-running tests 2. Optimize test performance 3. Consider parallel execution 4. Increase timeout if needed

Deployment Failed: "Workspace not found"

Problem: Cannot connect to Databricks workspace

Solution: 1. Verify Databricks host URL in secret 2. Check token is valid and not expired 3. Verify network connectivity 4. Check workspace permissions

Integration Tests Failed

db-cdc Project Overview

A real-time Change Data Capture (CDC) pipeline built on Azure Databricks + Apache Kafka, using Delta Lake as the storage layer and Power BI for analytics.

Architecture

Kafka Topics
    ↓
Bronze Layer  — raw, unprocessed CDC events (INSERT / UPDATE / DELETE)
    ↓
Silver Layer  — deduplicated, transformed, hash-tracked records
    ↓
Gold Layer    — aggregated, analytics-ready datasets for Power BI

Core Components

Jobs (src/jobs/)

File Purpose
kafka_ingest.py Streams raw messages from Kafka → writes to Bronze Delta table
cdc_processor.py Reads Bronze → deduplicates, adds MD5 change hash, handles soft deletes → writes Silver
data_quality.py Validates null %, duplicates, schema compliance, and data freshness across all layers

Notebooks (src/notebooks/)

Notebook Purpose
01_bronze_layer.py Kafka ingestion notebook for Databricks
02_silver_layer.py CDC transformation & deduplication
03_gold_layer.py Builds Power BI–ready Gold tables via build_dashboard_datasets()

Utilities (src/utils/)

File Purpose
schema_registry.py Schema management and evolution support
monitoring.py Metrics tracking and observability helpers
power_bi_dashboard.py Builds 5 Gold datasets for Power BI consumption

Power BI Gold Datasets

Dataset Description
cdc_statistics Record counts per source table and operation type
table_summaries Unique record counts and last-updated timestamps
daily_change_volume Day-level change aggregations
hourly_change_volume Hour-level change aggregations
pipeline_latency_summary Ingestion lag and processing latency metrics

Configuration (config/)

File Environment Notes
dev.yaml Development Local Kafka (localhost:9092), 2-worker cluster, 5-second trigger, 30-min auto-termination
prod.yaml Production Azure Event Hubs, auto-scaling cluster, 1-minute checkpoints

  • cdc_dashboard_measures.dax — DAX measures for calculated KPIs

Tests (tests/)

File Coverage

Technology Stack

Layer Technology
Streaming source Apache Kafka / Azure Event Hubs
Processing engine PySpark on Azure Databricks
Storage format Delta Lake (ACID transactions, time travel)
Orchestration Apache Airflow + Databricks Jobs
Infrastructure as Code Terraform
Analytics / BI Power BI
Monitoring Databricks Jobs UI + custom alerts (monitoring/alerts.yaml)
CI/CD GitHub Actions (see .github/)

Key Features

Feature Detail
Real-time CDC Capture and process INSERT / UPDATE / DELETE in real-time
Exactly-once semantics Guaranteed via Spark checkpointing + Delta Lake
Deduplication Keeps only the latest change per record using window functions
Soft deletes Deleted records are flagged (is_deleted) rather than removed
Change hashing MD5 hash of id + data used for efficient change detection
Schema evolution mergeSchema option handles upstream schema changes gracefully
Data quality Null checks, duplicate checks, schema compliance, and freshness checks
Auto-scaling Production cluster scales with data volume
Time travel Delta Lake versioning enables rollbacks and historical queries

Data Flow Detail

1. Source DB emits change events → Kafka topic (cdc_.*)
2. KafkaIngestJob reads stream → parses JSON → appends to Bronze Delta table
3. CDCProcessor reads Bronze stream
   ├─ Calculates MD5 change hash
   ├─ Flags DELETEs as is_deleted = true
   ├─ Deduplicates (latest record per ID wins)
   └─ Appends to Silver Delta table
4. Gold notebook reads Silver (batch)
   ├─ Normalises timestamps (epoch seconds or milliseconds)
   ├─ Aggregates into 5 analytics tables
   └─ Overwrites Gold Delta tables
5. Power BI connects to Gold tables via Databricks SQL connector
6. DataQualityValidator runs checks across all three layers
   └─ Saves validation reports; triggers alerts on failure
